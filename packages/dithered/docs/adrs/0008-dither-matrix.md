# 0008 — Configurable dither matrix

## Status

Proposed

## Context

`sampleCells` hard-codes the 4x4 Bayer matrix. Every cell gets
`threshold: (BAYER_4[j % 4][i % 4] + 0.5) / 16`, and there is no way to
swap it. At the default `cols = 16` the 4x4 tile repeats four times across
the grid and reads as grain. At `cols >= 32` it repeats eight or more
times and the eye resolves the tile itself: the output stops looking like
a dither and starts looking like a checkerboard.

Issue #8 (the PRD) asks for a `matrix` option covering `bayer2`,
`bayer4`, `bayer8`, a precomputed `blueNoise` table, and caller-supplied
custom matrices — with the default output byte-for-byte unchanged.

Two constraints shape the design:

- **The core is platform-free.** `packages/dithered/src/core/` and
  `shape.ts` have no DOM references, because `dithered/native` must not
  pull DOM code into a native bundle. Anything the matrix code touches
  inherits that constraint: no `document`, no `canvas`, no `fetch` of a
  noise texture at runtime.
- **`cell.threshold` is load-bearing.** Issue #5 (palettes) is being
  implemented in parallel against `cell.threshold`, and every `Brightness`
  function a user has written compares against it. The per-cell output
  shape cannot change; only how the number is produced.

The PRD also asks for a `thresholdFor(matrix, i, j)` helper so that the
palette PRD and the static-render PRD can share threshold assignment
rather than each reaching into `sampleCells`.

## Decision

Add a `matrix` option to `DitheredOptions`, defaulting to `'bayer4'`:

```ts
export type DitherMatrix =
  'bayer2' | 'bayer4' | 'bayer8' | 'blueNoise' | readonly (readonly number[])[];
```

A new platform-free module `packages/dithered/src/matrix.ts` owns the
matrices, their normalization, validation, and the tiling lookup.
`shape.ts` re-exports `BAYER_4` from it so existing deep imports keep
working.

### Bayer matrices are generated, not pasted

`BAYER_2` is the only literal:

```ts
const BAYER_2 = [
  [0, 2],
  [3, 1],
];
```

`bayerMatrix(order)` doubles it by the standard **quadrant-block**
recurrence — each quadrant is the previous matrix scaled by 4 with a
constant added, the constant taken from `BAYER_2`:

```
M_2n[b * n + j][a * n + i] = 4 * M_n[j][i] + BAYER_2[b][a]
```

for `a, b ∈ {0, 1}` and `i, j ∈ [0, n)`. So the four quadrants of
`M_2n` are `4M_n`, `4M_n + 2` on the top row and `4M_n + 3`,
`4M_n + 1` on the bottom.

This detail matters and is easy to get wrong: the _bit-interleaved_ form
(`M_2n[2j + b][2i + a] = 4 * M_n[j][i] + BAYER_2[b][a]`) is a different
matrix. Only the quadrant-block form reproduces the classic tables. A
test pins `bayerMatrix(4)` against the existing `BAYER_4` literal and
`bayerMatrix(8)` against the classic 8x8 table written out by hand, so a
regression here is caught rather than silently shipped as "some ordered
matrix".

`BAYER_4` and `BAYER_8` are computed once at module load
(`bayerMatrix(4)`, `bayerMatrix(8)`) and exported. `bayerMatrix` accepts
only powers of two `>= 2` and throws otherwise.

Cost: 4 numbers for `BAYER_2`, 64 for `BAYER_8`, all generated — nothing
pasted, nothing to mistype.

### Blue noise is a 16x16 table generated offline

`blueNoise` resolves to `BLUE_NOISE_16`: a **16x16** table of the ranks
`0..255`, each appearing exactly once, produced by Ulichney's
void-and-cluster method on a toroidal domain.

- **16x16, not 32x32.** 256 ranks is enough to break tiling at the sizes
  this library renders — the grid is `cols` wide and `cols` tops out
  around 64 in practice, so a 16-wide tile repeats at most four times,
  and unlike Bayer its repeat has no visible axis-aligned structure to
  latch onto. 16x16 costs ~1.1 kB of source and roughly 600 bytes
  minified; 32x32 would be four times that for no visible gain at these
  grid sizes.
- **Generated by a checked-in script, table committed.** The generator
  lives at `packages/dithered/scripts/blue-noise.mjs` and is wired up as
  `pnpm --filter dithered generate:blue-noise`. It writes
  `packages/dithered/src/blue-noise.generated.ts`, and **that file is
  committed**. The library never runs the generator: void-and-cluster is
  O(n² · filter) and belongs at author time, not at import time or in a
  build step consumers have to run.
- **Deterministic.** The initial binary pattern comes from a seeded
  mulberry32 PRNG with a fixed seed constant at the top of the script, so
  re-running it reproduces the committed table exactly. The script header
  records the seed and the Gaussian filter sigma (1.5, Ulichney's value).
- **The generated file is normal source.** It is not in
  `.prettierignore`, so it must be emitted prettier-clean (or `pnpm
format` run after regenerating) or `format:check` fails.

Validation of the committed table is by property, in `matrix.test.ts`:
the table is 16x16; its entries are exactly a permutation of `0..255`;
and — the property that distinguishes blue noise from white noise — the
minimum toroidal distance among the 16 lowest-ranked points is at least
2 cells. A white-noise table fails that last one routinely. If the
generator's output cannot satisfy it, the generator is wrong, not the
test.

### Normalization: integer ranks vs float thresholds

`resolveMatrix(matrix)` turns any `DitherMatrix` into:

```ts
export interface ResolvedMatrix {
  readonly width: number;
  readonly height: number;
  /** Row-major, `height` rows of `width` thresholds. */
  readonly thresholds: readonly (readonly number[])[];
}
```

The integer/float decision is made **once per matrix, from the whole
matrix** — never per entry, which would produce a mix of scales inside
one table:

- **Every entry an integer → rank mode.** Divisor `n = width * height`
  (the entry _count_, not the max entry, not the width). Threshold is
  `(v + 0.5) / n`. Entries must lie in `0..n - 1`. This is exactly the
  formula `sampleCells` uses today, so `BAYER_4` in rank mode reproduces
  today's thresholds to the bit.
- **Any entry non-integer → float mode.** Entries must lie in `[0, 1]`
  and are used as thresholds unchanged. No `+0.5` shift: the caller has
  already said where the threshold is.

The ambiguous case is a matrix whose entries are all integers but all
`0` or `1`. It is read as **ranks**, because the rule is stated in terms
of "are these integers", not "do these look like a 0..1 range". So
`[[0, 1], [1, 0]]` gives thresholds `0.125` and `0.375`, not `0` and `1`.
This is documented in the README and in the `DitherMatrix` jsdoc; a
caller who wanted thresholds should write `[[0.25, 0.75], [0.75, 0.25]]`,
which is non-integer and therefore unambiguous.

Rank mode does **not** require the entries to be a permutation. Ties and
gaps are allowed — a rank matrix is only an ordering, and rejecting ties
would rule out legitimate coarse patterns.

### Tiling

```ts
export function thresholdFor(matrix: DitherMatrix, i: number, j: number): number;
```

Resolves `matrix` and returns
`thresholds[j % height][i % width]` — **`j` (the row index) against
`height`, `i` (the column index) against `width`**. Getting this
backwards is invisible on square matrices (every built-in is square) and
badly wrong on a non-square custom one, so a test uses a deliberately
non-square 2x3 matrix and asserts the full tiled output over a grid
larger than the matrix in both axes.

`i` and `j` are grid indices and always non-negative in this codebase,
but `thresholdFor` uses a floored modulo (`((k % n) + n) % n`) anyway so
a caller passing a negative index gets a wrapped cell rather than
`undefined`.

### Resolution is memoized, so validation cost is paid once

`resolveMatrix` is memoized twice over:

- a `Map` keyed by name for the four built-ins, populated lazily;
- a `WeakMap` keyed by the array object for custom matrices, so
  `update({ matrix })` with a stable array reference does not re-validate,
  and holding the entry cannot leak the caller's array.

`ResolvedMatrix` objects are branded (a non-enumerable symbol) and
`resolveMatrix` returns an already-resolved input unchanged, so callers
that resolve once and call `thresholdFor` per cell pay a `WeakMap`/`Map`
hit rather than a revalidation. `sampleCells` resolves once up front and
calls `thresholdFor` in the loop.

### Validation errors

All errors are `Error` with the existing `dithered: ` prefix, thrown from
`resolveMatrix` — i.e. at `createDithered`/`update`/render time, with the
offending coordinates named, never once per cell:

| Condition             | Message                                                                                                         |
| --------------------- | --------------------------------------------------------------------------------------------------------------- |
| unknown name          | `dithered: unknown matrix 'foo'. Expected 'bayer2', 'bayer4', 'bayer8', 'blueNoise', or a 2D array of numbers.` |
| not an array / not 2D | `dithered: matrix must be a 2D array of numbers or one of the built-in matrix names.`                           |
| no rows               | `dithered: matrix must have at least one row.`                                                                  |
| empty first row       | `dithered: matrix must have at least one column.`                                                               |
| ragged                | `dithered: matrix is ragged: row 2 has 3 entries, but row 0 has 4.`                                             |
| non-finite entry      | `dithered: matrix[1][2] is not a finite number.`                                                                |
| rank out of range     | `dithered: matrix[0][0] is 20, outside the rank range 0..15 for a 4x4 matrix.`                                  |
| float out of range    | `dithered: matrix[0][1] is 1.5, outside the range 0..1 for a matrix with fractional entries.`                   |

The ragged case is called out in the PRD's acceptance criteria, so it
gets a message naming both the offending row and the expected width.

`resolveMatrix` also accepts a `ResolvedMatrix` — that is what lets a
caller resolve once and pass the result to `thresholdFor` per cell. Since
`ResolvedMatrix` is exported, a caller can hand-build one rather than
getting it from `resolveMatrix`, so recognition is **structural**, not
brand-based: an object carrying `width`, `height` and `thresholds` is
diagnosed _as a resolved matrix_ and validated on the same terms as any
other input, then returned branded and defensively copied. Gating the
pass-through on the private brand alone would make a value the signature
advertises fail with a message about malformed 2D arrays, which is worse
than no error at all. A structurally-invalid one gets its own errors:

| Condition              | Message                                                                       |
| ---------------------- | ----------------------------------------------------------------------------- |
| bad `width` / `height` | `dithered: resolved matrix width must be a positive integer, got 0.`          |
| row count mismatch     | `dithered: resolved matrix declares height 3 but thresholds has 2 rows.`      |
| row width mismatch     | `dithered: resolved matrix declares width 2 but thresholds[0] has 3 entries.` |
| non-finite threshold   | `dithered: resolved matrix thresholds[1][0] is not a finite number.`          |
| threshold out of range | `dithered: resolved matrix thresholds[0][0] is 5, outside the range 0..1.`    |

That last row matters more than it looks. `ResolvedMatrix.thresholds`
holds _thresholds_, not ranks, so `{ width: 4, height: 4, thresholds:
BAYER_4 }` is a plausible thing to write and it typechecks — and without
a range check it would be accepted verbatim, giving every cell a
threshold of 0.5 to 15.5 and drawing essentially nothing, silently. The
range check turns the ADR's own "wrong in a way no error message would
ever surface" failure mode into a loud one.

### Plumbing

- `sampleCells(shape, cols, hitTest, rows?, matrix?)` — a fifth optional
  parameter, defaulting to `'bayer4'`. Appending rather than reordering
  keeps every existing call site working; PR #3 already changed this
  signature once and a second breaking change in the same release is not
  worth the tidiness.
- `DitheredOptions.matrix?: DitherMatrix`, `DEFAULTS.matrix = 'bayer4'`.
- The web renderer's `configure()` already resamples on every `update()`,
  so passing `opts.matrix` into `sampleCells` is the whole change there —
  `update({ matrix })` resamples and rebuilds the sprite strip on the
  same path as `update({ cols })`.
- **A rejected `update()` leaves the instance untouched.** Validation now
  throws from `configure()`, and `update()` merges the patch into the
  live options before calling it — so without care an invalid `matrix`
  would commit the whole patch, halt the loop, and then re-throw on every
  later `update()`, bricking the instance for good. `configure()`
  therefore resamples (the step that can throw) before mutating anything,
  and `update()` applies the merged options as a candidate it reverts on
  failure. The error still propagates; the instance keeps its options,
  its surface and its running loop.
- `dithered/react` forwards `matrix` in the create effect, in the
  `update()` effect's payload **and in that effect's dependency array**.
  Omitting the dep is the failure mode that makes `update({ matrix })`
  silently do nothing on the React path.
- `dithered/native`: `useDitheredPictures` takes `matrix`, passes it to
  `sampleCells`, and lists it in its `useMemo` deps; `<Dithered>`
  forwards the prop. When the caller passes pre-sampled `cells`, `matrix`
  is ignored — the thresholds are already baked into those cells. That is
  documented on the prop rather than made an error, matching how `cols`
  and `rows` already behave with `cells`.
- Custom matrices are compared by identity in both React dependency
  arrays, exactly as `shape` and `brightness` already are; the README
  gains the same "hoist it to module scope" note those props carry.

## Alternatives considered

**Pasting the 8x8 table as a literal.** Shorter, and the classic table is
easy to find. Rejected: the PRD asks for generation, a mistyped entry in a
64-number literal is invisible in review, and the recurrence is four
lines. The literal survives as a _test fixture_ instead, which is where a
hand-written copy is actually useful.

**Generating blue noise at runtime, or at build time.** Void-and-cluster
on 16x16 takes tens of milliseconds — tolerable once, intolerable per
instance, and it would put a loop with a PRNG in the import path of a
library whose whole pitch is "nothing else to install". A build step
would push the same cost onto consumers. A committed table is a few
hundred bytes and costs nothing.

**32x32 blue noise.** Four times the bytes. At `cols <= 64` the 16x16
tile already repeats at most four times with no axis-aligned structure,
so the extra 3 kB buys nothing visible. Revisit if `cols` in the hundreds
ever becomes a real use case.

**Inferring rank-vs-float per entry** (`v > 1 ? rank : threshold`).
Rejected outright: a matrix with a mix of small and large entries would
get a mix of scales, producing a pattern that is wrong in a way no error
message would ever surface.

**Deciding rank-vs-float from the maximum entry** (`max <= 1 → float`).
Tempting, and it resolves the all-0/1 ambiguity in the "nicer"
direction. Rejected because it silently changes meaning based on the
data: a coarse 4x4 rank matrix that happens to use only ranks 0 and 1
would flip to float mode and produce thresholds of `0` and `1` — cells
that always draw or never draw. "Is it an integer" is a property of the
type the caller wrote, not of the values that happen to be in it.

**Replacing `cell.threshold` with a matrix reference on the cell** and
resolving thresholds at paint time. Cheaper to resample, and it would let
`update({ matrix })` skip the hit-test entirely. Rejected: issue #5 is
being implemented in parallel against `cell.threshold`, and every
user-written `Brightness` reads it. The saving is a hit-test that already
only runs on reconfigure.

**A `DitherMatrix` class or builder.** More room for future options
(rotation, per-instance offset). Rejected as premature; the PRD's union
type is plain data, serializes, and matches how `Shape` is already
modelled in this codebase.

## Consequences

- Default output is unchanged: `'bayer4'` resolves to `bayerMatrix(4)`,
  which equals the `BAYER_4` literal, normalized by the same
  `(v + 0.5) / 16` formula `sampleCells` uses today. A snapshot test
  makes that a hard guarantee rather than an argument.
- `cell.threshold` keeps its type and its range, so issue #5's palette
  work needs no coordination beyond the merge.
- `sampleCells` grows a fifth parameter. Callers who pass four arguments
  are unaffected.
- Bundle grows by roughly 1 kB minified: the blue-noise table dominates,
  and it is only pulled in by the entries that import `matrix.ts` — which
  is all of them, since `sampleCells` needs it. Tree-shaking the table
  out would mean a separate export path; not worth the API surface at
  this size.
- The generated blue-noise file is a committed artifact. If someone edits
  it by hand, nothing catches the drift beyond the property tests; the
  file header says not to.
- Custom matrix validation throws rather than falling back to `bayer4`.
  A typo is now a loud failure at create time instead of a quietly wrong
  pattern.

### Tests to write

In `packages/dithered/src/matrix.test.ts`:

1. `bayerMatrix(2)` equals `[[0, 2], [3, 1]]`.
2. `bayerMatrix(4)` deep-equals the classic 4x4 table, written out as a literal in the test — the same values `shape.ts` holds today.
3. `bayerMatrix(8)` deep-equals the classic 8x8 table, written out as a literal in the test.
4. `bayerMatrix(n)` output is a permutation of `0..n² - 1` for `n` in `2, 4, 8, 16`.
5. `bayerMatrix` throws for `0`, `1`, `3`, `6`, `-4` and non-integers.
6. `resolveMatrix('bayer4')` reproduces `(BAYER_4[j][i] + 0.5) / 16` for every cell — the today-formula, pinned.
7. Named matrices all resolve to thresholds strictly inside `(0, 1)`, with the right `width`/`height`.
8. `resolveMatrix` returns the identical object for repeated calls with the same name, and for repeated calls with the same array reference (memoization).
9. Rank mode: a custom integer matrix normalizes by entry count, e.g. `[[0, 1], [2, 3]]` → `[[0.125, 0.375], [0.625, 0.875]]`.
10. Rank mode allows ties and gaps: `[[0, 0], [3, 3]]` resolves without throwing.
11. Float mode: `[[0.1, 0.9], [0.5, 0.25]]` passes through unchanged (no `+0.5` shift).
12. The all-integer `[[0, 1], [1, 0]]` is read as ranks, not floats — asserts `0.125`/`0.375`, pinning the documented tie-break.
13. Validation: ragged, empty, zero-width, `NaN`, `Infinity`, rank above `n - 1`, negative rank, float above 1, negative float, unknown name, non-array — each throws, and each message matches on its distinguishing substring.
14. `thresholdFor` tiles a **non-square** 2 wide x 3 tall matrix correctly over a 5x7 grid: every `(i, j)` matches `thresholds[j % 3][i % 2]`, asserted for all 35 positions.
15. `thresholdFor` accepts a name, a raw array and an already-resolved matrix, and agrees across all three.
16. `thresholdFor` wraps negative `i`/`j` instead of returning `undefined`.
17. Blue noise: `BLUE_NOISE_16` is 16x16; its entries are exactly the permutation `0..255`; the minimum toroidal distance among the 16 lowest-ranked points is `>= 2`.

In `packages/dithered/src/shape.test.ts`:

18. **The default-output snapshot.** `sampleCells(shapes.rozenite, 16, hitTest)` with no `matrix` argument produces cells whose `threshold` values match a committed inline snapshot; a sibling assertion checks the same cells against the literal `(BAYER_4[j % 4][i % 4] + 0.5) / 16` expression, so the guarantee survives even if someone regenerates the snapshot. Run it at `cols = 16` (the default) and once at `cols = 33`, a size where the tile does not divide the grid evenly.
19. `sampleCells(..., 'bayer8')` and `sampleCells(..., blueNoise)` produce thresholds in `(0, 1)` and a threshold set that differs from the default at the same `cols`.
20. `sampleCells` with a custom matrix tiles it, and with a ragged one throws.

Assert through the recording paint context — a run with `brightness` fixed at a value that sits between two thresholds draws a different cell count under `bayer8` than under `bayer4`.
